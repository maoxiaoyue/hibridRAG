# 2026-07-02 工作日誌

（回溯補記：本篇由 `agent_client/CLAUDE.md` 原本的「歷史沿革」表格與現狀說明重建，非即時工作日誌，沒有逐步決策過程的原始記錄）

## 一、視窗（GUI）工具背景啟動模式（`ToolSpec.Background`）

### 問題

使用者登錄的一般工具走 `exec.CommandContext`，會**等待程式結束**才拿到 stdout/stderr。GUI 程式（記事本、小畫家、瀏覽器…）不會自己退出，逾時後被強制砍掉、回傳失敗——這類工具無法用一般工具模式開啟。

### 修法

登錄工具頁新增「視窗程式（只負責開啟，不等待關閉）」勾選項 → `ToolSpec.Background=true` → `ExecuteTool` 改走新的 `launchBackground()`：`cmd.Start()` 啟動、獨立 goroutine 呼叫 `cmd.Wait()` 回收子行程避免 zombie、不綁 ctx 也不套 timeout，立即回傳「已啟動 PID N」。

### 測試

`tool_service_test.go`：`TestExecuteTool_Background_ReturnsImmediately`（`timeout /t 5` 模擬長駐程式，斷言 2s 內就拿到回傳）、`TestExecuteTool_Background_LaunchError`（命令不存在的錯誤路徑）。

## 二、內建 Coding Agent（`code_service.go` + `diff_dialog.go` + `Config.WorkspaceRoot`）

### 背景

使用者問「agent_client 可以幫我編輯、修改程式嗎？」，選擇要「像 Claude Code 一樣的完整改碼流程」——與工具頁的使用者登錄工具（allowlist 外部程式）不同，這組是 client 內建、比照 Claude Code 的 Read/Grep/Edit/Write 語意。

### 新增 5 個內建工具

| 工具 | 語意 | 審核 |
|---|---|:---:|
| `code_list_files` | 列出相對目錄下的檔案/子目錄（非遞迴，跳過 `.git/.hyp/node_modules/vendor/bin/obj/.vs/.idea`） | 否 |
| `code_search` | 遞迴文字搜尋（不分大小寫子字串），略過 >2MB 檔案，上限 50 筆 | 否 |
| `code_read_file` | 讀檔，`offset`/`limit` 行數窗口，上限 `maxReadBytes=8000` bytes 並註明截斷 | 否 |
| `code_edit_file` | `old_string`→`new_string` 精確替換；找不到或不唯一（未帶 `replace_all`）明確回錯 | **是** |
| `code_write_file` | 整檔覆寫/新建（`os.MkdirAll` 建父目錄） | **是** |

### 關鍵設計決策

- **路徑安全**（`resolveInWorkspace`）：`filepath.Join(absRoot, rel)` 後用 `filepath.Rel` 檢查結果是否仍在 workspace root 內；真的逃逸（如 `../outside.txt`）**明確回錯**給 LLM 而非靜默鉗制到別的路徑——讓 LLM 知道自己給錯路徑可以自己修正，且不會誤以為寫到了它以為的位置。
- **diff 審核閘門**（`applyWithDiff`，`code_edit_file`/`code_write_file` 共用）：讀出舊內容 → `difflib.UnifiedDiff` 產生 unified diff → 呼叫 `DiffApproveFunc(path, diffText) bool`（client 端由 `chat_view.go` 的閉包接到 `views/diff_dialog.go` 的 `showDiffApproval()`：`dialog.NewCustomConfirm` 顯示唯讀等寬 diff，「套用」/「拒絕」兩鈕，同步阻塞等使用者回應）→ 核准才 `os.MkdirAll`+`os.WriteFile`；拒絕回傳明確錯誤（`IsError=true`），讓 LLM 可據此調整方案。
- **二進位/非文字檔防護**：所有讀寫路徑都先 `utf8.Valid(data)` 檢查，非法 UTF-8（多半是二進位檔）一律明確拒絕。
- **已知限制**：本地小模型（`gemma4:e4b`，8B）在多檔案/複雜重構上遠不如雲端大模型可靠，適合單檔小改動；後端 `config.yaml` 的 `tools.max_iterations: 8` 是每輪對話的伺服器端工具迴圈上限，複雜任務可能不夠跑完（後端調參，不在 agent_client 範圍）；只支援文字檔讀寫，不支援真正的多檔案 diff/refactor 規劃（一次只處理一個工具呼叫）。

### 測試

`code_service_test.go`（18 cases，`t.TempDir()` 隔離）：路徑逃逸防護、manifest 開關、list/search/read（含截斷與二進位拒絕）、edit（找不到/不唯一/核准/拒絕/replace_all）、write（新建含父目錄/拒絕不寫入）、diff 格式基本檢查。

## 三、對話頁 Normal／Code 模式切換按鈕（雙重開關）

### 使用者要求

「Normal 模式不會進入編輯狀態，只會使用工具或執行指令」——避免只設過一次工作目錄就永遠處於「可編輯」狀態。

### 實作

`chatTab`（`chat_view.go`）新增 `codeMode` 狀態（預設 `false` = Normal）：
- Normal 模式一律傳空字串當 `workspaceRoot` 給 `NewChatEngine`（`BuiltinCodeTools("")` 回 nil，manifest 完全不含碼工具）——即使設定頁已經設過工作目錄也一樣。
- Code 模式才傳設定頁的實際工作目錄。

雙重開關（工作目錄已設 **且** 模式切到 Code）都要打開才會把碼工具交給 agent，任一個沒開都會讓 `workspaceRoot` 被清成空字串。按鈕本身 `widget.Button`，`Importance` 依模式切換（`MediumImportance`/`WarningImportance`）做視覺區分；點切到 Code 但工作目錄未設時彈 `dialog.ShowInformation` 提示去設定頁。

## 小結

這三項變動共同構成「內建 Coding Agent」功能的完整安全模型：背景啟動解決 GUI 工具逾時問題（獨立能力，不限於 coding agent）；diff 審核 + 路徑逃逸防護解決寫入風險；雙重開關解決「忘記自己在 Code 模式」的誤觸風險。
