## 二、agent_client CJK 字型渲染修復（兩輪嘗試，最終改走純英文 UI）

### 背景
使用者回報 `agent_client`（Fyne 桌面 client）畫面上所有中文（分頁標籤、按鈕、表單標籤）都顯示成方塊/問號菱形（tofu boxes）——螢幕截圖顯示「對話」「上傳文件」等分頁文字全部無法渲染。

### 第一輪嘗試：自訂 CJK 主題（失敗）
新增 `app/views/theme.go`：包一層 `fyne.Theme`，只覆寫 `Font()`，嘗試載入 Windows 內建中文字型（`msjh.ttc`/`msyh.ttc`/`mingliu.ttc`/`simsun.ttc`）。`a.Settings().SetTheme(newCJKTheme())` 接進 `main_view.go`。

**根因**：這四個候選字型全部是 `.ttc`（TrueType Collection）容器格式；Fyne 底層字型解析（`golang.org/x/image/font/sfnt`）**不支援 `.ttc`**，讀檔本身不會報錯（`os.ReadFile` 成功），但 Fyne 實際上無法用它渲染文字，靜默退回內建預設字型——症狀與完全沒修一樣（使用者回報「問題還是一樣」）。

### 第二輪嘗試：改用單一 .ttf + sfnt.Parse 驗證（仍不理想）
改選 Windows 內建的**單一** TrueType 檔（非容器）：`kaiu.ttf`（標楷體，繁中）優先，`simhei.ttf`/`simfang.ttf`/`simkai.ttf`（簡中）備援；`loadCJKFontResource()` 用 `golang.org/x/image/font/sfnt.Parse` 驗證可解析性才採用。額外寫了一次性腳本用 `sfnt.GlyphIndex` 驗證 `kaiu.ttf` 確實涵蓋畫面上用到的所有中文字（對話/上傳文件/工具/知識圖譜/設定等），glyph 全部命中。

**結果仍不理想**：使用者回報「這個問題更嚴重了」——畫面截圖顯示文字雖然不再是方塊，但渲染出現明顯的視覺瑕疵/字形錯位（推測是 Fyne 對 `kaiu.ttf` 這類書法風格字型在小像素下的 hinting/快取問題，非本次能簡單排除的範圍）。

### 最終決定：捨棄 CJK 字型方案，全面改用英文 UI
使用者明確要求：「用英文就好，不要用中文」。做法：
1. 刪除 `theme.go`，`main_view.go` 移除 `SetTheme()` 呼叫，回到 Fyne 預設主題。
2. 全面掃描（`rg` 比對 CJK Unicode 範圍 `[\x{4e00}-\x{9fff}]` 落在字串字面值內，非註解）並翻譯所有會被 Fyne 渲染或送進對話/LLM 的中文字串為英文：
   - 5 個分頁標題、`chat_view.go`/`upload_view.go`/`tools_view.go`/`settings_view.go`/`graph_view.go`/`diff_dialog.go` 的所有 label/placeholder/button/dialog 文字
   - `app/services/errors.go` 的 typed error catalog（E3001–E3005 訊息）
   - `code_service.go` 的 5 個內建碼工具的 `Description`/JSON Schema `description` 欄位、所有工具執行結果/錯誤訊息（這些會進到與 LLM 的對話內容，理論上有機會被引用回覆進聊天視窗）
   - `tool_service.go` 的背景視窗程式啟動訊息、`chat_service.go` 的工具執行狀態列文字
   - `main_view.go` 的 3 行 log 訊息（雖然只寫進 log 檔不經 Fyne 渲染，仍一併翻譯以求一致）
3. **保留不動**：所有程式碼註解（沿用專案既有的全中文註解慣例，不受這次「畫面顯示語言」的修正影響）。
4. `code_service_test.go` 有一則斷言比對舊中文子字串（`"還有"`），同步改成新的英文子字串（`"more lines not shown"`）。
5. 移除 `theme.go` 後執行 `go mod tidy`，`golang.org/x/image` 退回 `// indirect`（原本因 sfnt 驗證而升成 direct），`github.com/pmezard/go-difflib` 仍維持 direct（`code_service.go` 本來就直接用它產生 diff）。
6. `go build`/`go vet`/`go test ./...` 全綠。

**對未來的我**：Windows 內建中文字型幾乎都是 `.ttc` 容器（`msjh`/`msyh`/`simsun`/`mingliu` 等雙字重合併檔），Fyne（至少 v2.4.5，底層走 `golang.org/x/image/font/sfnt`）不支援這個格式——如果之後又要幫 Fyne app 加中文顯示，**不要**直接指到這些常見路徑，要先找單一 sfnt 檔（如 `simhei.ttf`/`simkai.ttf`/`kaiu.ttf`）或想辦法從 `.ttc` 抽出單一字型再包成 `fyne.Resource`；即使字型能被 `sfnt.Parse` 成功解析、glyph 也涵蓋所需字元，仍可能在實際渲染時出現視覺瑕疵（本次 `kaiu.ttf` 的狀況），值得先用小範圍畫面驗證再全面套用，不能只靠程式碼層級的 parse 成功就斷定沒問題。

## 三、agent_client 新增讀取 AGENTS.md 作為 Coding 模式 system prompt

### 需求
使用者要求：`agent_client` 進行程式開發（Code 模式）時，讀取工作目錄下的 `AGENTS.md`，作為這次對話的 prompt 設定主體——比照 Claude Code 等工具讀 `AGENTS.md`/`CLAUDE.md` 取得專案專屬指示的慣例。

### 設計與實作（`app/services/chat_service.go`）
- 新增 `loadAgentsMDPrompt(workspaceRoot string) string`：讀 `filepath.Join(workspaceRoot, "AGENTS.md")`；`workspaceRoot` 空、檔案不存在、非合法 UTF-8、或內容全空白時回傳空字串（呼叫端不送這則訊息，行為等同沒有這個功能）。內容超過 `maxAgentsMDBytes`（20000 bytes）時截斷並註明，比照 `code_service.go` 既有的截斷訊息風格。
- `ChatEngine.Send()`：只在 **新對話的第一輪**（`e.sessionID == ""`）才呼叫 `loadAgentsMDPrompt` 並把結果包成 `Role: "system"` 的訊息，插在 `user` 訊息之前一起送出；同一 session 的後續輪次不會重送（避免每輪都重複佔用 context 預算）。`chat_view.go` 每次 `send()` 都會建立新的 `ChatEngine`，但透過閉包變數 `sessionID` 延續狀態，因此「`e.sessionID == ""`」精準對應「這個對話串的第一次送出」，不受 UI 層重建 engine 影響。
- **後端相容性確認**（未改動後端程式碼）：`agents/app/controllers/agent_grpc.go` 的 `protoRoleToChat()` 已原生支援 `"system"` 字串（映成 `services.RoleSystem`），`agent_chat.go` 的 `ChatSync` 會把 `req.Messages` 裡的每一則訊息依序 append 在 persona 自己的 system prompt 之後——最終送給 LLM 的順序會是「persona system prompt → AGENTS.md system 訊息 → 使用者訊息」，不需要動後端。
- 只在 Code 模式生效：`workspaceRoot` 在 Normal 模式下一律是空字串（`chat_view.go` 既有邏輯），`loadAgentsMDPrompt("")` 直接回空，等於功能自動關閉，沿用「雙重開關」的既有安全設計，不需要另外加開關。

### 測試
新增 `app/services/chat_service_test.go`（6 cases）：空/空白 root 停用、檔案不存在、正常讀取內容、空白內容檔案、非 UTF-8 拒絕、超長截斷。`go build`/`go vet`/`go test ./...` 全綠。

**已知限制**：`AGENTS.md` 只在工作目錄根部找，不會往上層目錄查找（跟 `code_service.go` 其他工具的路徑解析慣例一致，只認工作目錄本身）；沒有處理多個 AGENTS.md 分層合併（例如子目錄各自有一份）的情境，因為目前的 Coding Agent 工具本身也是整個工作目錄扁平存取，沒有子專案分層的概念。
