## 一、Phase 1 — Event Bus（Redis Stream）

### 動機
架構 v2 圖明確標示「⚡ Event Bus（Redis Stream + Kafka）」為**新增**元件。Phase 1 先補 Redis Stream（Kafka 留 Phase 6 按需）。

### 設計決策

**為何 Redis Stream 而非 Kafka 起步？**
- 現有 Redis 連線可直接複用，不引入新依賴
- XADD / XREADGROUP API 簡單夠用
- 量級夠（單 stream 萬級 ops/sec）

**為何「best-effort」不阻斷主流程？**
- 事件不是 source of truth（PG 才是）
- 事件是「通知」用途，遺失不影響業務正確性
- 失敗只記 log，避免拖累主請求延遲

**為何兩個 eventbus 套件不共用？**
- 避免兩服務間的編譯期耦合
- 套件實作極小（~250 行），複製成本低於共享 module 的維護成本
- 未來可考慮抽 shared module，現在不過度工程

### 主要檔案

| 服務 | 檔案 | 關鍵類型 |
|------|------|---------|
| agent_embedding | `internal/eventbus/redis_stream.go` | `Publisher` interface, `RedisStream`, `Consumer` preview, `Event{Type,AgentID,Payload}` |
| agents | `internal/eventbus/redis_stream.go` | 同上（獨立複製） |

### 串接點

**agent_embedding** 在 `EmbeddingService` 加 `WithEventBus()` + `emitEvent()`：
- `UpsertChunks` 成功 → `embedding.upserted`（含 chunk_ids、model、dimension）
- `SearchByText` 成功 → `embedding.searched`（含 top_k、hits、query_len；**不含 query 文字**，隱私）
- `DeleteByDoc` 成功 → `embedding.deleted`

**agents** 在 `IngestService` 加 `WithEventBus()` + `emit()`：
- `markRunning` → `ingest.started`
- `markDone(nil)` → `ingest.completed`（含 done_chunks、total_chunks、duration_ms）
- `markDone(err)` → `ingest.failed`

### 設計細節
- `MAXLEN ~ 10000` 環形緩衝，舊事件自動丟棄（不會 OOM）
- `XADD` 用 timeout context（預設 1s），失敗不阻塞 caller
- `Source` 欄位寫入服務名（`agent_embedding` / `agents`），方便消費端過濾
- 統一 Event 結構：`{type, agent_id, trace_id, source, timestamp, payload}`，payload 為 JSON-serialized map

## 三、ContextBuilder + process() 接入 RAG（P0-1 + P0-3）

### 架構討論（重要）

事前先和使用者確認**歸屬問題**——哪些功能該放 Agent 內部、哪些該歸 Shared Service：

| 項目 | 歸屬決定 | 理由 |
|------|---------|------|
| ContextBuilder | **Agent 內部** | 配額策略需依 SKILL.md persona 調整；架構圖中無此服務節點 |
| HybridSearcher / RRF | **Vector Search 服務**（過渡期：agent_embedding） | 架構圖明確標示「dense / sparse / hybrid (RRF)」是 Vector Search 能力 |
| process() 接 RAG | **Agent 內部** | 推理 orchestration 是 Agent 核心職責 |
| Sparse 向量寫入 | **Embedding + Vector Search** | 架構圖分工：Embedding 算 sparse，Vector Search 存/查 |
| EpisodicMemory 寫入 | 過渡期 Agent，終態 agent_memory（事件驅動） | v2 拆分後改為訂閱 `agent.outbound` 事件 |

### ContextBuilder 設計

**位置**：`agents/internal/agent/context/builder.go`

**核心介面**：
```go
type MemoryReader interface {
    GetPersonalByAgent(ctx, agentID) (*PersonalMemory, error)
    ListProceduralByAgent(ctx, agentID, limit) ([]ProceduralMemory, error)
    ListEpisodicByAgent(ctx, agentID, limit) ([]EpisodicMemory, error)
}

type RAGSearcher interface {
    SearchByQuery(ctx, agentID, query, topK) ([]vectordb.SearchHit, error)
}

type Builder struct{ memory; rag; defaults Quotas }

func (b *Builder) Build(ctx, agentID, query, parsed *persona.ParseResult, instruction string) (*BuildResult, error)
```

**配額三層 fallback**（重要設計）：
1. SKILL.md `Identity.context_*` keys（最高）
2. `config.context.*`（中）
3. builtin（1/3/5/2，最低）

任一層 < 0 → 退到下一層。

**為何要三層？**
- builtin 確保「插即用」
- config 讓 ops 統一調整
- SKILL.md 讓 agent 作者自訂配額（客服 agent 想要更多 episodic、技術 agent 想要更多 RAG）

**SKILL.md 寫法範例**：
```yaml
## Identity
- name: SupportBot
- role: Customer Support
- context_episodic: 5      # 客服需要更多過去對話
- context_procedural: 5
```

### 並發 4 路 + 容錯

```go
go GetPersonal()     // fallback：instruction 為空時補
go ListProcedural()  // fallback：同上
go SearchByQuery()   // 總是查；query 空則跳過
go ListEpisodic()    // 總是查
WaitGroup → 組裝 system prompt
```

**容錯關鍵設計**：任一來源失敗只記錄 errs，**其他來源仍正常組裝**。RAG 服務 down 不會讓整個推理失敗，只是少一段 context。

### MemoryService 擴充

加了 3 個查詢方法（給 ContextBuilder 用）：
- `GetPersonalByAgent(ctx, agentID)` — agent_id 為 unique，回單筆
- `ListProceduralByAgent(ctx, agentID, limit)` — `ORDER BY updated_at DESC`
- `ListEpisodicByAgent(ctx, agentID, limit)` — `ORDER BY occurred_at DESC`

**為何先用時間排序而非相似度？**
- procedural 沒有 embedding 索引（待 Phase 2 升級）
- episodic 同上
- 「最近活躍」是合理的初版啟發式

### persona.ParseResult 加 ContextQuotas

新增 `ParseResult.ContextQuotas() ContextQuotas`，從 `Identity` map 抽出 `context_personal` / `context_procedural` / `context_rag` / `context_episodic` 整數值（支援 string / int / float64）。

### process() 升級

**舊版**：
```go
instruction := s.loadInstruction(...)
LLM.Chat(instruction + user_messages)
```

**新版**：
```go
parsed, instruction := s.loadPersona(...)  // 同時回 ParseResult（給 quotas 解析用）
query := lastUserContent(messages)
result := s.ctxBuilder.Build(ctx, agentID, query, parsed, instruction)
LLM.Chat(result.SystemPrompt + user_messages)
```

`loadInstruction` 改名為 `loadPersona`（同時回 `*ParseResult` 和 instruction），呼叫端只更新一個地方。

`WithContextBuilder()` 為**鏈式注入**，未注入時 process() 自動退到 instruction-only 模式（向後相容）。

### 測試（11 cases，全綠）

`internal/agent/context/builder_test.go`：
- RAG + Episodic 注入
- Persona quotas 覆蓋 defaults
- instruction 空 → DB fallback
- query 空 → 不查 RAG
- nil RAG injector → 純記憶模式
- ErrNotFound 容錯
- nil memory → panic

## 四、HybridSearcher / RRF（P0-2）

### 為何放 agent_embedding 而非 agents

架構圖明確：Vector Search 服務（:50055）= dense + sparse + hybrid (RRF)。
agent_embedding 是 Vector Search 服務的**前身**（Phase 4 會拆出獨立 binary）。

過渡期把 hybrid 邏輯放這裡，未來拆分時整個 service 層搬過去即可，agents 只需把 `vectordb.HTTPClient` 從 HTTP 改 gRPC，介面不變。

### 設計決策

**RRF vs Weighted-Sum？選 RRF。**
- ✅ 不需正規化（dense cosine ∈ [-1,1] vs sparse BM25 ∈ [0,∞)）
- ✅ 對 outlier 穩健
- ✅ 學界 + 業界（Microsoft / Vespa / Elasticsearch）標配
- ✅ 公式簡單：`score = Σ 1/(k + rank_i)`

**SparseSearcher 為什麼是 interface？**
- 三種策略並存：FTS（立即可用）/ SPLADE（需資料）/ nop（disabled）
- 未來可加 BM25 / 向量索引等實作不破壞 caller

**為何加 PostgreSQL 依賴？**
架構圖顯示 Vector Search 服務同時連 Cassandra 和 PostgreSQL：
- Cassandra：dense 向量 ANN
- PostgreSQL：sparse 向量 / FTS 索引（agents migration 003 已建好 `chunks` / `chunks_sparse` 表）

agent_embedding 加 PG 連線後可讀這些表（不寫，因為寫是 ingest 路徑的職責）。

**為何用 lib/pq + database/sql 而非 bun？**
- 不需 ORM（純 SELECT）
- 輕量、零學習成本
- 與 agents 的 bun 完全解耦

### 三種 sparse 策略

| 策略 | 後端 | 何時用 |
|------|------|------|
| `fts`（預設） | PG `to_tsvector('simple', text)` | 立即可用，不需 sparse 向量 |
| `splade` | `chunks_sparse.token_weights` JSONB 點積 | TEI backend 啟用後 |
| `auto` | splade 優先，無資料 fallback 到 fts | 漸進切換 |

`auto` 策略的精妙處：當 `chunks_sparse` 開始寫入資料時，**不需要改 config 也不需要重啟**就會自動切換到 SPLADE。

### 純函式 FuseRRF

```go
func FuseRRF(lists [][]SearchHit, k int) []SearchHit
```

可獨立測試（無外部依賴），且：
- tie-break by ChunkID（確定性輸出）
- 跨 list 自動補齊缺欄位（list1 有 Text、list2 有 DocID → 融合後都有）
- k=0 自動 fallback 到 DefaultRRFK（60）

### HybridSearcher 並發

```go
go h.dense.SearchByText(...)   // Cassandra ANN
go h.sparse.Search(...)         // PG
sync.WaitGroup → FuseRRF → top-K
```

**容錯**：任一路失敗仍嘗試另一路；**兩路皆失敗才報 500**。

### `POST /api/search/hybrid` 端點

請求參數：
- 必填：`agent_id`, `query`
- 選填：`dense_top_n`（20）、`sparse_top_n`（20）、`final_top_k`（5）、`rrf_k`（60）、`min_score`（0）

回應含觀測欄位：`dense_count` / `sparse_count` / `rrf_k`，方便監控各路命中數。

### 設定檔結構

```yaml
postgres:
  enabled: true
  dsn: "postgres://..."
  max_open_conns: 10

hybrid:
  enabled: true
  dense_top_n: 20
  sparse_top_n: 20
  final_top_k: 5
  rrf_k: 60
  sparse_strategy: "fts"   # fts | splade | auto
```

`hybrid.enabled: false` 或 PG 未連線 → endpoint 自動回 503，**不影響其他 endpoint**。

- 跨 list 欄位填補
- k=0 fallback

## 設計反思與決策亮點

### 1. 把「介面」當作未來服務拆分的橋樑
ContextBuilder 的 `MemoryReader` 介面今天由 `*MemoryService` 滿足；
未來 agent_memory 拆出後，介面不變，只需換成 `*MemoryGRPCClient`。

`SparseSearcher` 同理：未來 Vector Search 服務拆出後，agent_embedding 端的實作不需改 — 是 agents 端的 vectordb 客戶端要改。

### 2. 容錯比正確性更重要（在 RAG 場景）
RAG 不像支付，少一段 context 不會出大錯，但**整個推理鏈卡住**會直接破壞用戶體驗。
所有新元件都採「best-effort + 降級」：
- ContextBuilder：任一路失敗仍組裝
- HybridSearcher：兩路失敗才報錯
- EventBus：失敗只記 log

### 3. 配額三層 fallback 是設計亮點
這個 pattern 同時兼顧「插即用」、「ops 統一調整」、「per-agent 自訂」三個需求，且向後相容（不寫 SKILL.md context_* 自動退到 config 預設）。

未來其他「依 agent 客製化」的需求（例如 LLM model 選擇、temperature 等）可以複用同樣的三層 fallback 模式。

### 4. RRF 純函式設計
`FuseRRF([][]SearchHit, k) []SearchHit` 是純函式，可獨立測試（不需 PG / Cassandra）。
8 個測試案例全部不需任何 mock infrastructure，跑得超快（μs 級）。

純函式邊界 + interface 注入 = 最少測試 setup 成本。
