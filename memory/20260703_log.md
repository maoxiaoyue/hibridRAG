## 一、agent_gateway 路由修正

### 問題
`x-skill` 直接當下游 `agent_id` 轉發；registry 裡的 skill-id 命名空間跟舊測試殘留資料（`agent-a`/`agent-b`，指向已死的 `localhost:18080`）互撞，容易路由到錯的/死的 agent——因為 `Search()` 原本用 substring match，殘留資料的 skill 名稱只要「包含」查詢字串就會命中。

### 修正
`agent_registry/app/services/registry_service.go` 的 `Search()` 改兩段式：
1. 先做**精確 skill-id 比對**（`WHERE lower(s->>'id') = skill`）
2. 無精確符合才 fallback 到原本的 substring match（`LIKE '%skill%'`）
3. 同分依 `last_seen_at DESC` 排序，優先最近活躍的 agent

`agent_registry/app/controllers/registry.go` 加 `distinctAgentCount()`，`SearchAgents` 若結果橫跨 >1 個不同 agent 會記警告 log（可觀測性，不阻斷）。

## 二、全服務 HTTP/2 + 真 TLS

### 決策過程
一開始問使用者 h2c 還是 TLS+h2（未即時回覆），先實作了 h2c；使用者後續明確要求：「使用真的 TLS + h2，接複用 agents/scripts/gencert/ 幫其他 4 個服務也生憑證」。

**為何最終選真 TLS 而非 h2c？**
- 使用者明確指示；且真 TLS 更貼近生產環境的傳輸層安全基準
- `agents/scripts/gencert/` 已有現成的自簽憑證產生器可直接複用，不需重新設計

### 實作
- 5 個服務的 `config.yaml`：`server.protocol: http` → `http2`，加 `server.tls: {enabled: true, cert_file, key_file}`
- `scripts/gencert/main.go` 複製到 `agent_gateway/` `agent_registry/` `agent_memory/` `agent_embedding/`，各自 `go run ./scripts/gencert` 產生 `certs/server.crt` + `server.key`
- 憑證用 ECDSA P-256、10 年效期、覆蓋 localhost/127.0.0.1/::1，且 `IsCA: true`（自己簽自己，可當自己的 CA 用）
- 內部 HTTP client（`agent_gateway/app/services/registry_client.go`、`agents/internal/agent/vectordb/http_client.go`）改用 `http2.ConfigureTransport` + `TLSClientConfig{InsecureSkipVerify: true}`（dev 環境跳過憑證驗證）

## 五、agents 改真 gRPC 呼叫 agent_memory（核心變動）

### 背景
稽核發現 `agent_memory` 服務雖然已經寫好，但完全沒被用——`agents` 一直維持自己直連同一個 Postgres 的重複實作（`app/controllers/memory.go`）。使用者要求：「把 agents 改成真的透過 gRPC 呼叫 agent_memory」。

### 實作
1. **proto 契約**：`agent_memory/proto/memory.proto`（package `agent_memory.v1`，service `MemoryService`），`agents/proto/memory.proto` 幾乎相同拷貝（只有 `go_package` 不同）。用 `google.protobuf.Struct` 傳 jsonb 欄位，避免手動 JSON 字串編碼。
2. **agent_memory 端**：`app/controllers/memory_grpc.go`（`MemoryGRPCServer`）實作全部 RPC，委派給既有的 service 層方法；`main.go` 加 gRPC server（`:8510`，走同一張 HTTP 憑證的 TLS）
3. **agents 端**：`app/services/memory_grpc_client.go`（`MemoryGRPCClient`）實作 client 端所有方法，介面對齊既有的 `EpisodicWriter` 等介面（例如 `CreateEpisodic` 不帶 ctx 參數，內部用 `context.Background()`）
4. **main.go 切換邏輯**：定義 `memoryBackend` 介面（6 個方法的聯集），依 `cfg.Memory.GRPCAddr` 是否為空決定用 `MemoryGRPCClient`（gRPC）還是 fallback 回 `MemoryService`（直連 DB，過渡期相容）

### 為何保留 fallback？
`agents/app/controllers/memory.go`（`agents` 自己的 `/api/memory/*` REST 代理）目前仍是直連 DB，尚未一併轉換——這是已知的殘留範圍，留給未來收斂。gRPC 連不上時退回舊路徑，避免單一依賴點造成服務不可用。

## 六、補齊 6 類記憶中缺的 3 類（本日主要工作量）

### 稽核起點

### 6-1. Semantic Memory

**設計**：`agent_memory` 早就有 `LongTermMemoryService`（Cassandra + BGE-M3 1024 維向量 + SAI ANN），但從未被 `agents` 呼叫過，也從未真正跑過一次。

補上的鏈路：
- proto 加 `CreateLongTerm` / `SearchLongTerm` 兩個 RPC
- `agents/app/services/semantic_memory.go`（`SemanticMemory{embed, mem}`）：`Write()` 把文字丟去 embed 再存進 Cassandra；`Search()` 反過來查
- `internal/agent/context/builder.go` 加第 5 路並發抓取（`SemanticSearcher` 介面），系統提示詞新增「## Things You Know (Semantic Memory)」段落
- `internal/agent/persona/parser.go` 加 `context_semantic` SKILL.md override
- `tool_builtin.go` 的 `memory_read`/`memory_write` 加 `kind=semantic`

**過程中揪出兩個從沒被跑過的潛伏 bug**（`agent_memory` 早就存在，但因為從未被呼叫過所以沒被發現）：

1. **Cassandra 表從未建立**：`internal/cassandra/init.go` 完全沒有 schema 建立邏輯（不像 `agent_embedding` 有 `EnsureSchema`）。第一次 `grpcurl` 測 `CreateLongTerm` 直接報 `table long_term_memory does not exist`。修法：補 `EnsureSchema(ctx)`，建表 + 3 個 SAI index（含 `similarity_function: COSINE`），`main.go` 連上 Cassandra 後無條件呼叫。

2. **gocql 無法直接 marshal `[]float32` 進向量欄位**：修完表之後還是失敗，錯誤變成 `can not marshal []float32 into custom(...VectorType...)`——gocql v1.7.0 對 CQL 原生 vector type 沒有內建支援。發現 `agent_embedding` 早就用一個 `CQLVector` wrapper type（實作 `gocql.Marshaler`/`Unmarshaler`，big-endian float32 串接，CEP-30 wire format）解過同一個問題，直接原封不動搬進 `agent_memory/app/services/vector_marshal.go`，包住兩處呼叫點。`grpcurl` 驗證後 `CreateLongTerm`/`SearchLongTerm`（ANN 命中）都成功。

**順帶修正**：`agents/config/config.yaml` 的 `embedding.provider`/`tei_endpoint`/`model` 三個 key 本來寫在 YAML 裡但從沒對應到任何 Go struct 欄位（死設定），且值本身也是錯的（`provider: "tei"` 卻指向 Ollama 埠、`model` 用 HF repo 格式而非 Ollama tag 格式）。對照 `agent_embedding` 已驗證可用的設定（`backend: ollama`、`model: "bge-m3"`）修正後才接活。

### 6-2. Shared Memory（跨 agent 共用池）

**設計**：新的 PG 表 `shared_memory`，`(pool_id, key)` 複合唯一鍵（用 Bun 的 `unique:同名group` tag 技巧達成），`Upsert` 用 `ON CONFLICT (pool_id, key) DO UPDATE`。

- `agent_memory`：新增 `models/shared_memory.go`、`services/shared_memory_service.go`（`Get`/`Upsert`/`List`）
- proto 加 `GetShared`/`UpsertShared`/`ListShared` 三個 RPC
- `agents/config.go` 加 `AgentConfig.PoolID`（同 pool_id 的 agent 互相可讀寫）
- `tool_builtin.go` 加 `kind=shared`（`memory_read` 沒給 key 就 List，給了就 Get；`memory_write` 需要 `pool_id`+`key`+`value`）

**設計上刻意避開的一個坑**：一開始考慮把 nil 的 `*MemoryGRPCClient` 直接指派進 `SharedReaderForTool`/`SharedWriterForTool` 介面欄位，這會踩 Go 經典的「nil interface trap」——因為 `MemoryGRPCClient` 的方法不是 nil-receiver-safe（不像 `SemanticMemory` 特意做成 nil-safe）。實作前發現了這點，改成宣告真正 nil 的介面型別區域變數，只在 `memIsGRPC` 分支內才賦值，完全繞開這個陷阱，並在 `agents/main.go` 留了註解說明原因。

### 6-3. Short-term Memory（多輪對話 session buffer）

**設計**：Redis-backed `SessionStore`，整段 session 用一個 JSON blob 存（`SET`/`GET` 整包，不用 Redis list），key 格式 `chat:session:{agentID}:{sessionID}`。

- `agents/app/services/session_store.go`：`Load()` 缺 key 回 `(nil, nil)`（非 error）；`Append()` 讀舊的、加新的、裁到 `maxTurns`（丟最舊的）、重新序列化、`SET` 帶 TTL
- 兩個方法都做成 nil-receiver-safe——Redis 沒連上（`cache.GetClient()` 回 nil）時整個機制自動停用，退回改動前的單輪行為，不會 panic
- `agent_chat.go` 的 `ChatSync`：`sessionID` 提前算好，組 `msgs` 前先從 Redis 撈歷史插進去；新增 `saveSessionTurn()`，在兩個「推理結束」的回傳點（非工具呼叫分支、工具迴圈終止分支）各呼叫一次，跟既有的 `writeChatEpisodic()` 平行存在

**為何用整包 JSON blob 而非 Redis List？**
- 讀寫都是「整個 session」為單位，沒有「只取最新一則」的需求
- 裁剪邏輯（丟最舊的保留 maxTurns）用陣列切片比操作 Redis List 的 LTRIM 語意更直覺
- TTL 用單一 key 的過期時間就夠，不需要額外維護

## 對未來的我：要點提醒

1. **`agent_memory` 的 `LongTermMemoryService` 現在是真的能動了**，但 Cassandra schema 建立（`EnsureSchema`）跟連線建立一樣是「best-effort」——沒接上 Cassandra 不會讓整個服務掛掉，只是 semantic memory 相關功能會退化。

2. **gocql 的 vector 欄位一律要包 `CQLVector(...)`**，不能直接塞 `[]float32`。這條規則同時適用 `agent_embedding` 和 `agent_memory`，兩邊的 `vector_marshal.go` 是同一份程式碼的兩份拷貝（刻意不共用 module，理由同 Event Bus 的「複製成本低於共享維護成本」）。

3. **`agents/main.go` 裡凡是要把 `*MemoryGRPCClient` 塞進介面型別欄位，一定要先確認該介面的方法是不是 nil-receiver-safe**。`SemanticMemory` 特意做成 nil-safe（因為呼叫端可能沒配置 embedding），但 `MemoryGRPCClient` 本身沒有做這層防護，直接塞值可能踩 nil-interface-trap——用區域變數延遲賦值來繞開。

4. **`agents/app/controllers/memory.go`（REST `/api/memory/*` 代理）仍是直連 DB**，是已知殘留範圍，尚未跟 gRPC 化一併處理。之後若要收斂到只剩一條記憶存取路徑，這是下一個要動的地方。

5. **`chat_session` 短期記憶預設 40 則、TTL 2 小時**，Redis 沒連上時自動停用退回單輪行為——這是刻意的降級設計，不是 bug。若未來要做「session 過期後仍想留存」的需求，要另外設計持久化路徑（目前設計是純快取，過期即丟）。

6. **三個新記憶機制的驗證腳本都用 `//go:build ignore` + 用完即刪**，不是留在 repo 裡的測試基礎設施。若之後要做真正的整合測試，建議比照 `agents/tests/`（`//go:build integration`）的既有模式，而非重新發明。
