### ADK 核心抽象

|------|------|------------------|
| `agent.Agent` interface | `Run(ctx) iter.Seq2[*Event, error]` 事件流 | 對應 gRPC Inbound 推理鏈 |

| `remoteagent.NewA2A` | 跨 agent HTTP/JSON 協定 | 對應 GrpcDispatcher |

## 二、`persona.ToInstruction()` 實作

### 原因
TODO.md 中 #2 System Prompt Design 是 8 步驟框架最致命的缺口。`persona.Parse()` 已能取得 Identity + ExpressionDNA + MentalModels，但目前只能寫 DB，無法直接餵 LLM。`ToInstruction()` 補齊這條路徑。

### 設計決策

**為什麼用 Markdown 結構（`##` / `###`）**
LLM 訓練資料中絕大多數 system prompt 是 Markdown 格式，模型對這個結構最熟悉。

**為什麼 map iteration 一律字典序排序**
Go map 是隨機 iteration，會導致同一 SKILL.md 每次渲染的 prompt 不同，破壞 prompt cache hit rate。MentalModels **不**排序，因為順序通常代表優先級（First Principles 在前是有意的）。

**中英文 alias 設計**
parser 已經支援中文 section 標題，渲染端不能砍這個一致性：
- `name`/`名稱`/`名字` → opening name slot
- `role`/`角色` → opening role slot
- `domain`/`領域`/`領域範圍` → opening domain slot
其餘 keys 進入 `## About You` 區塊。

**空 result 回傳空字串而非預設值**
保持純函式語意；fallback 策略由呼叫端決定。

**Identity 中的 `name`/`role`/`domain` 移到 opening line**
避免「You are A, B」與下方「## About You\n- name: A」重複。

### 輸出範例
```
You are 小柴, 程式設計助理. Your domain is Go 後端開發.

## About You
- expertise: gRPC, PostgreSQL, RAG, 系統設計
- language: zh-TW

## Communication Style
- avoid: 過度禮貌、贅詞、emoji 氾濫
- style: 先給結論，再補理由
- tone: 直接、簡潔，不寒暄

## Mental Models

### 先驗證後實作
寫程式碼前先確認需求邊界...

Heuristics:
- check_existing: 先看現有實作再決定新增/修改
- minimal_diff: 改動範圍越小越好
```

### 測試結果
- 新增 8 個測試（Full / Empty / OnlyIdentity / ChineseAliases / AgentNameFallback / NoMentalHeuristics / AboutYouOmitsOpeningKeys / DeterministicOutput）
- 加 1 個 godoc `Example` 測試 — **一字不差比對輸出格式**（regression 防漂移最強的方式）
- 全部 PASS（10 既有 + 8 新增 + 1 example = 18 cases）

## 三、LLM Client 實作（5 個檔案）

### 原因
TODO2.md ⚡ 步驟「LLM Generate」尚未有任何 Go 實作；config/llm.yaml 雖列出 Ollama/OpenAI/Anthropic 設定，但 `app/services/` 只有 embedding client 沒有 chat client。`ToInstruction()` 完成後最自然的下一步就是接通 LLM 呼叫。

### 設計決策

**統一介面 `LLMClient`**
```go
type LLMClient interface {
    Chat(ctx, ChatRequest) (*ChatResponse, error)
    Provider() string
}
```
`Chat()` 同步呼叫；`Provider()` 回 provider 字串便於 log/metrics。

**為什麼三家 API 內部表達不一樣，對外要抽掉**
- OpenAI / Ollama：system 放在 `messages` 陣列裡的第一個
- Anthropic：`system` 是 top-level 欄位，**不能**放進 messages 陣列
我們對外統一用 `[]ChatMessage{{Role: RoleSystem, ...}, ...}`，client 內部 `extractSystemAndRest()` 處理 Anthropic 的特殊情況。這讓呼叫端不必管 provider 差異。

**custom provider 走 OpenAI-compatible 協定**
業界自架 LLM 服務（vLLM、LM Studio、LocalAI、Ollama 的 OpenAI-compatible endpoint）幾乎都實作 OpenAI `/v1/chat/completions` 格式。讓 `provider: custom` 走同一條路徑，只差 `BaseURL` 與選擇性的 `api_key`（自架可以沒有）。

**Gemini 故意不實作**
ADK 已內建 `google.golang.org/adk/model/gemini.NewModel`，重複包裝沒有價值。當未來接 ADK runner 時，直接用官方那個即可；我們的 `LLMClient` 是給「不走 ADK 的場景」用的（如 ingest 中的 LLM chunker、CLI demo、stub handler）。

**MVP 不做 streaming**
gRPC Inbound 是 unary 模式，串流不是現在的瓶頸。`ChatRequest.Stream` 欄位先保留位置，未來加 `StreamingLLMClient` 介面時不影響既有 caller。

**TokenUsage 統一**
三家 API token 欄位名不同（OpenAI: `prompt_tokens`、Anthropic: `input_tokens`、Ollama: `prompt_eval_count`），統一成 `TokenUsage{PromptTokens, CompletionTokens, TotalTokens}`，cost tracking 只看一個地方。

## 五、`cmd/llm-demo` CLI + 範例 SKILL.md

### 原因
LLM client 的單元測試只能驗證**單一函式**，無法驗證**整條鏈**。需要一個端到端工具：SKILL.md → Parse → ToInstruction → Chat → 列印回應，肉眼判斷 prompt 品質與 LLM 回應是否符合 persona 設定。

### 設計決策

**單輪 + REPL 兩種模式**
- 單輪：`--prompt "..."` 一次性執行
- 互動：未給 `--prompt` 進入 REPL，**保留 conversation history**（這是測 LLM 多輪一致性的關鍵）

**REPL 內建指令**
- `exit` / `quit` / Ctrl+D — 結束
- `reset` — 清掉對話 history（保留 system prompt），方便切換話題

**輸出統計：`[model | tokens (in/out) | finish_reason | turn]`**
每次回應都顯示，方便：
1. 估 cost（in tokens × 單價 + out tokens × 單價）
2. 偵測 prompt 漏注入（如果 in tokens 很小代表 instruction 沒進去）
3. 偵測截斷（finish_reason=length）

**範例 SKILL.md：「小柴」**
特意設計成中文 + 英文混用、3 個風格鮮明的 mental models（先驗證後實作 / 介面分離 / 錯誤訊息要可診斷），可立即看出 LLM 是否吸收 persona 設定。

## 六、後期：`config/llm.yaml` 改用 `${VAR:-default}` env-var 風格

### 原因
使用者表示 192.168.50.104:11434 上 Ollama 的 port 要換。為避免每次改 port 都要修 yaml，改成 env-var 覆寫風格：
```yaml
url: "${OLLAMA_URL:-http://192.168.50.104:11434}"
model: "${OLLAMA_MODEL:-gemma4:e4b}"
```

### 改動
1. **`llm_loader.go` 的 `expandEnvVars`**：原本只支援 `${VAR}`，擴充正則支援 `${VAR:-default}`
   ```regex
   \$\{([A-Za-z_][A-Za-z0-9_]*)(?::-([^}]*))?\}
   ```
2. **保留原有行為**：純 `${VAR}` 找不到 env 仍保留字面（讓 Validate 能診斷）；`${VAR:-default}` 找不到才用 default
3. **新增測試** `TestParseLLMConfig_EnvWithDefault`：分別驗證「env 未設用 default」與「env 有設覆蓋 default」兩種路徑

### 驗證
```bash
# 未設 env → 用 yaml default
go run ./cmd/llm-demo ...
# url=http://192.168.50.104:11434

# 設 env → 覆蓋
OLLAMA_URL="http://192.168.50.104:11500" go run ./cmd/llm-demo ...
# url=http://192.168.50.104:11500
```

兩種路徑均驗證成功。**使用者只要 `export OLLAMA_URL=...` 即可切換 port，不需要改 yaml。**

## 十一、gRPC Inbound 端到端串接（當日追加完成）

### 完成項目

**`app/controllers/agent_grpc.go`（新建）**

實作 `models.AgentServiceServer` 介面，完成「最小可運作 agent」：

```
InboundReq
  ├── 驗證（nil payload / empty messages / missing agent_id）
  ├── 採番 message_id（msg_<16 hex>）
  ├── 立即回 InboundAck{accepted:true}
  └── goroutine: process()
        ├── SkillLoader.Get → Load（cache miss 時從磁碟讀）
        ├── persona.Parse(pack.Body).ToInstruction() → system prompt
        ├── buildChatMessages(instruction, proto messages)
        ├── LLMClient.Chat(ChatRequest{messages, temperature})
        └── sendReply() → OutboundMsg{To:req.From, Direction:"reply", content}
                └── Dispatcher.Send()
```

設計決策：
- **fire-and-forget goroutine**：Inbound 用 gRPC Unary 立即 ack，LLM 推理（最多 120s）在背景非同步跑，caller 不等待
- **`context.Background` 傳給 goroutine**：避免 gRPC 連線關閉後推理被 cancel
- **nil LLM / nil Dispatcher 容錯**：standalone mode 下只 log，不 panic
- **SkillPack 容錯**：找不到 SKILL.md 不中止，以空 system prompt 繼續推理
- **`SkillProvider` 介面**：抽掉 `*services.SkillLoader` 直接依賴，讓測試可注入 stub
